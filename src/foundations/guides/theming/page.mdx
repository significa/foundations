## Overview

A polished interface is layered: an app frame, a canvas, cards and popovers over it, controls on those, and edges that tell you which is which. Foundations names each layer by its **role**, so a theme is a set of values, and the same components can look flat, outlined, raised or embossed without changing their source.

## Surfaces

| Token                          | Role                                                                                    |
| ------------------------------ | --------------------------------------------------------------------------------------- |
| `--color-background`           | The canvas the app sits on.                                                             |
| `--color-panel`              | Anything raised over it: cards, panels, popovers, menus, dialogs, drawers, toasts.      |
| `--color-background-secondary` | A region set apart from the canvas: sidebars, wells, app frames.                        |
| `--color-control`              | The face of inputs, outline buttons, checkboxes and segmented controls.                 |
| `--color-border`               | Edges of controls and surfaces. Translucent, so the step is the same on every surface.  |

Two rules keep them composable:

- **Name tokens by role, never by region.** `--color-sidebar` or `--color-toolbar` only fit one layout; when a sidebar needs a fill, use `background-secondary` or `surface`, and when it needs a new shade, change the value of the role.
- **Steps are relative.** In dark mode shadows don't read, so `panel` is a step lighter than the canvas and `control` is a translucent veil that's always a step lighter than whatever it sits on. Borders are translucent for the same reason, and so are the fills components draw inside a layer (hover, highlighted items, tracks: `bg-foreground/5`). Keep the steps between layers small; a few points of lightness is enough. Prefer translucent values when you add your own steps.

### Borders

`--color-border` is translucent, so the same line works on every layer. That holds as long as each line is drawn once over a filled layer. Two cases need care:

- **Seams.** Where two bordered elements touch, drop one side (`border-r-0`, `divide-*`) instead of overlapping them with a negative margin; overlapped translucent lines darken.
- **Lines as fills.** A track, skeleton or gridline drawn with the border colour as a background stacks with whatever is under it. Use `bg-foreground/5` or a solid colour for fills, and keep `--color-border` for lines.

For a fainter hairline inside a layer, use `border-border/60`.

### Cards

There's no Card component: a card is a surface with a resting edge.

```tsx
<section className="rounded-xl border border-border bg-panel shadow-panel">…</section>
```

### Dark regions

A dark bar inside a light page (a selection toolbar, a promo strip) needs no extra tokens. Put `scheme-dark` on the container and give it a fill: every token inside resolves to its dark value, so text, controls and borders adapt.

```tsx
<div className="bg-[oklch(25%_0.06_270)] text-foreground scheme-dark">…</div>
```

Shadows are the exception: they're baked in at build time (see Gotchas), so a raised theme keeps its light-mode edge inside the region.

## Depth comes from edges

Many designs separate layers with edges, not fills: a card the same colour as the page with a white inner rim and a grey outer one, or a button with a highlight on top and a darker bottom edge. Look at edges up close before reaching for another background colour.

Controls and resting surfaces take their edge from tokens, and the press from two more:

| Token                      | Role                                                                     |
| -------------------------- | ------------------------------------------------------------------------ |
| `--shadow-control`         | The resting edge of buttons, inputs, checkboxes, radios and slider thumbs. |
| `--shadow-control-pressed` | What the edge collapses to while a button is pressed.                    |
| `--shadow-panel`         | The resting edge of a surface: cards, bordered tables, file rows.        |
| `--press-scale`            | How much a button shrinks when pressed (`0.98` by default).              |
| `--press-offset`           | How far a button sinks when pressed (`0px` by default).                  |

`--shadow-panel` is for a panel in the flow; `--shadow-sm` to `--shadow-lg` stay for things that float: popovers, menus, dialogs, toasts. Keep resting edges weaker than floating ones, so a card never reads as a popover.

### Recipes

Each recipe replaces values in your `@theme`; components don't change.

Flat, edges from borders only:

```css
@theme {
  --shadow-control: 0 0 #0000;
  --press-scale: 1;
}
```

Raised: a highlight on top, a darker bottom edge and a soft contact shadow. Pressing sinks the control instead of shrinking it.

```css
@theme {
  --shadow-control:
    inset 0 1px 0 light-dark(oklch(100% 0 0 / 0.9), oklch(100% 0 0 / 0.06)),
    0 1px 0 light-dark(oklch(0% 0 0 / 0.08), oklch(0% 0 0 / 0.4)),
    0 2px 3px oklch(0% 0 0 / 0.07);
  --shadow-control-pressed: inset 0 1px 1px oklch(0% 0 0 / 0.06);
  --press-scale: 1;
  --press-offset: 1px;
}
```

Embossed: controls keep the colour of what they sit on; a white inner rim and the border do the work.

```css
@theme {
  --color-control: transparent;
  --shadow-control: inset 0 0 0 1px oklch(100% 0 0 / 0.9), 0 1px 0 oklch(0% 0 0 / 0.07);
  --shadow-control-pressed: inset 0 1px 2px oklch(0% 0 0 / 0.08);
  --press-scale: 1;
  --press-offset: 1px;
}
```

## Control heights

Buttons, inputs, selects, toggles and pagination share one height scale, so a button and an input of the same size line up side by side:

| Token                 | Default |
| --------------------- | ------- |
| `--control-height-xs` | 24px    |
| `--control-height-sm` | 32px    |
| `--control-height-md` | 40px    |
| `--control-height-lg` | 48px    |

Retune them in `@theme` to change every control at once. `--button-height` and `--input-height` still override a single control. Roundness stays on `--radius`: the radius steps derive from it, and each step can be overridden in `@theme` on its own.

## Badge colours

Every [Badge](/ui/badge) variant is one colour: fill, ring and text derive from `--badge-color`. Status variants map to `--color-success`, `--color-error` and the rest; any other colour is a class away, with no new variant:

```tsx
<Badge className="[--badge-color:var(--color-violet-600)]">Story video</Badge>
```

`--badge-fill` and `--badge-ring` set the strength of the tint (10% and 20%; the neutral variant uses 5% and 10%), and `--badge-text` the text colour. A solid badge is a fill at full strength:

```tsx
<Badge variant="success" className="[--badge-fill:100%] [--badge-text:var(--color-background)]">New</Badge>
```

Set them in a class, or in the base of `badgeStyle` when a design's badges are all solid.

## Selected toggles

A pressed [Toggle](/ui/toggle) is a faint tint by default. For a solid chip, set the pressed fill and text; hover moves the fill toward the text colour either way:

```tsx
<Toggle className="[--button-pressed-bg:var(--color-foreground)] [--button-pressed-text:var(--color-background)]">
  Selected
</Toggle>
```

## Custom tokens and `cn`

`cn` merges conflicting classes with tailwind-merge, which only knows Tailwind's own theme names. A custom shadow such as `shadow-raised` isn't recognised as a shadow, so it sits beside a component's `shadow-control` instead of replacing it, and whichever comes later in the stylesheet wins. Register custom names in `src/lib/utils/classnames.ts`:

```ts
const twMerge = extendTailwindMerge({
  extend: { theme: { shadow: ["control", "control-pressed", "raised"] } },
});
```

Colour names need no registration; shadows, text sizes and radii do.

## Gotchas

- **Tailwind inlines shadow values.** `shadow-control` compiles to the value in `@theme`, not to `var(--shadow-control)`, so overriding `--shadow-control` on an element does nothing. Change shadows in `@theme`. Colours (`bg-control`) are variables and can be overridden anywhere.
- **`light-dark()` only takes colours.** Gradients, percentages and lengths that differ between themes need a `[data-theme="dark"]` (or `prefers-color-scheme`) rule instead.
- **Children paint over inset edges.** An `inset` shadow on a panel is covered by the backgrounds of its children; draw it on an `after:` overlay (`after:pointer-events-none after:absolute after:inset-0 after:rounded-[inherit] after:shadow-…`) when children are filled.
- **Corners.** Squircles come from one `@supports` block at the end of the setup CSS, together with the radius bump that compensates them. Delete the block for plain round corners.
